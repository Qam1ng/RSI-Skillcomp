# 预注册：口1 实验 —— 宏目录注入的配对测量

登记时间：2026-10-19（跑之前写定，跑完不改口径）。

## 问题

把已验证的宏目录交给 harness 自己的 agent，它写的程序会不会更短、更快成功？
（上一阶段的 5/5 是我们手拼的调用；这次由 agent 自己规划。）

## 设计

- **底盘**：ASPIRE cap-harness，LIBERO-Pro，ucla A6000(GPU2)。
- **agent**：tools/aspire_gemini_driver.py 的"生成→跑→读工件→修"环，
  gemini-flash-latest，max 5 轮。**环内无人**：失败证据由 failure_digest() 从
  运行工件自动生成。
- **两臂（配对，同任务同种子同样例同轮上限）**：
  - A 对照：驱动原样（API 文档 + 2 个跨任务获胜程序样例）。
  - B 处理：同上 + 宏目录（pick_object/place_into 的签名、PRE/EFF、返回键），
    宏实现由驱动在执行前拼到程序头部（口1 的"目录给规划者、实现给运行时"）。
- **任务**：挖掘未见过的 pick-place 任务（挖掘用过 libero_goal_task/2、
  libero_object_swap/0、libero_spatial_swap/2，一律排除）。选取规则：
  在 libero_goal_task 套件里按 task-id 从小到大，取第一个指令为
  "put/place X in/on Y"形的未见任务做试点；扩展时同规则取后续任务。
- **开发种子** 51（与 b 档战役同口径）；**泛化验证**：各臂的最终成功程序
  跑 seeds 56–60 批（init-mode seeded）。

## 量什么（都带出处，判定一律用基准检查器）

1. 成功率：开发种子上几轮内成；泛化批 5 种子过几个。
2. 到首成的轮数与 token（prompt/output 分开报——B 臂提示天然更长，不混算）。
3. 程序文本的决策点：agent 所写程序的 AST 调用数（宏调用算 1）。
4. 宏采用率：B 臂程序里宏调用占比；agent 是否绕开目录裸写。

## 预期（跑前写死）

- B 臂程序调用数显著更少（两位数 → 个位数）。
- B 臂到首成轮数 ≤ A 臂。
- 若 B 臂 agent 无视目录裸写 API，本身就是重要负结果（目录的提示工程不够），如实报。

## 停机条件

- 每臂每任务 ≤5 轮；两臂都 5 轮未成 → 该任务记双失败，停，不加轮。
- 试点（1 任务 × 2 臂）跑完先出报告，扩任务前过一次人工核。
- 预算：flash 档，试点合计预计 <10 万 token（约几美分）；超 3 倍预估即停。
